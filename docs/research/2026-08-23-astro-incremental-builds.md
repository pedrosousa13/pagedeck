# Astro and Incremental Static Builds (August 2026)

**Date:** 2026-08-23
**Status:** Complete. Primary sources only (docs.astro.build, github.com/withastro/astro releases + CHANGELOG + issues/PRs, github.com/withastro/roadmap RFCs, astro.build/blog, npm registry metadata). No secondary blog write-ups were used as evidence.
**Question:** Does Astro support incremental static builds as of August 2026 — rebuilding only the pages affected by a content change, rather than the whole site? And if so, what exactly does it cache: data, rendered HTML, or emitted files?
**Method note:** Where a source's own wording is load-bearing, it is quoted verbatim. GitHub API was used directly for issue/PR state, merge dates and release timestamps rather than relying on rendered pages. Anything dated 2026 was fetched live; nothing in the 2026 window is from recall.

---

## Verdict

**Yes — Astro shipped real incremental static builds on 2026-08-06 in Astro 7.2.0, behind `experimental.incrementalBuild`. It caches rendered page output (the generated HTML files), not just fetched data. The maintainer's suspicion is correct, and my earlier claim that incremental builds are our single strongest differentiator versus Astro is no longer true as stated.**

Precisely what it is:

- It skips the **generation** phase for unchanged pages: when a route's code hash and a path's user-supplied `cacheKey` both match the previous build, "Astro copies the earlier output instead of rendering the page again." That is genuine **output caching backed by render skipping** — strictly stronger than data caching.
- It does **not** skip the **sync** or **bundling** phases. The dependency hash is computed *from* the Rolldown bundle output during the build, so content sync + full bundle still run on every build. Incremental savings are bounded to render time only.
- It is **opt-in per path and manual**: only paths returned from `getStaticPaths()` that return a `cacheKey` string are eligible. Static (non-dynamic) routes and endpoints are explicit non-goals. Astro does not detect content changes on its own — "The correctness of each path's `cacheKey` is the user's responsibility."
- It requires `build.concurrency === 1`.
- It produces **no partial output**. `dist/` is emptied at the start of every build and skipped pages are restored into it from `cacheDir`. Every build still yields a complete `dist/`, and no API tells you which pages were skipped.

What remains genuinely differentiated for us (see §7): (a) automatic change detection without a user-authored cache key, (b) incremental behaviour for *all* routes rather than dynamic routes only, (c) skipping the bundle/sync phase, not just generation, (d) an emitted change manifest enabling manifest-diff partial redeploy, and (e) the 50k-page scale envelope itself, where Astro has documented OOM failures and no published guidance.

## 1. Current state: `experimental.incrementalBuild` (Astro 7.2.0)

**Shipped:** `astro@7.2.0`, published **2026-08-06T10:48:55Z** (npm registry metadata; GitHub release `astro@7.2.0` published 2026-08-06). Current latest is `astro@7.2.4`, published **2026-08-19T14:43:52Z** (npm `dist-tags.latest`).

**Status: experimental.** Documented under experimental flags, `Since v7.2.0`:
<https://docs.astro.build/en/reference/experimental-flags/incremental-build/>

> "This experimental feature reuses the output of a previous build so that unchanged pages are not rendered again.
>
> When enabled, Astro can skip a static page generated by `getStaticPaths()` if both its data and the code it depends on are unchanged since the last build. You mark a page's data by returning a `cacheKey` for it, and Astro tracks the code by hashing the page's module dependency graph. When both match the previous build, Astro copies the earlier output instead of rendering the page again."

Works in a plain static build with no adapter — the feature is defined entirely in terms of prerendered pages, and the RFC's non-goals exclude SSR: "Incremental behavior for on-demand (SSR) routes. This RFC covers prerendered pages only."

**What is cached — precisely.** From the RFC's "Cache storage" section
(<https://github.com/withastro/roadmap/blob/stage-3%2Fincremental-static-builds/proposals/0062-incremental-static-builds.md>):

> "- A manifest (`incremental-build.json`) records, per route, the dependency hash and, per path, the `cacheKey` and the relative output file path.
> - The rendered output files are stored under a `dist/` subdirectory of `cacheDir`."

So the cached artifact is the **emitted HTML file**, plus a manifest of hashes. Not fetched data (that is the content layer's job, §3), and not an intermediate render tree.

**The two-part invalidation model.** From the RFC:

> "The user's `cacheKey` covers *data*. The **dependency hash** covers *code*.
>
> During the build, Astro walks the transitive module graph of each prerendered page (its template, layouts, components, and imported utilities and assets) and hashes both the sorted set of module identifiers and each module's compiled output. Hashing the compiled output produced during bundling, rather than the source files on disk, means the hash also covers virtual modules that have no file on disk but still contribute generated code."

> "Content entry data modules are deliberately excluded from this walk. If they were included, editing a single content entry would change the dependency hash and force every path on the route to re-render."

**This is the load-bearing architectural constraint for us:** the dependency hash is derived from *compiled output produced during bundling*. Bundling is therefore not skipped. Astro still runs content sync and a full Rolldown bundle on every incremental build; only the per-page render is skipped.

**Opt-in, manual keys.** Docs:

> "Only pages returned from `getStaticPaths()` that include a `cacheKey` can be skipped. Every other page, including static pages that do not use `getStaticPaths()`, is rendered on each build."

RFC non-goals:

> "- Incremental behavior for static (non-dynamic) routes. Dynamic routes already have a mechanism for loading data, so there is a natural place for providing a cacheKey, where a new mechanism would need to be created for static routes.
> - Automatically detecting content or external data changes. The correctness of each path's `cacheKey` is the user's responsibility; Astro does not infer when a CMS entry or other external data has changed."

The RFC is candid about the resulting UX cost, under Drawbacks:

> "Requiring a `cacheKey` may not meet user expectations. Developers who hear 'incremental builds' often expect Astro to figure out what changed on its own. Asking them to supply and reason about a key, and to accept that a wrong key silently serves stale pages is less appealing than an automatic system would have."

> "We might fail to invalidate the cache when we should. … Any gap here produces stale pages that look correct, which is harder to notice than an outright build failure."

**Documented limitations** (docs page, "Limitations"):

- `build.concurrency > 1` disables the cache entirely — "Astro logs a warning and re-renders every page."
- Server islands: re-rendered every build unless a stable `ASTRO_KEY` is set.
- Middleware: "Changes to your middleware do not invalidate cached pages. … run `astro build --force` after editing it."

**Global invalidation.** Docs: "Changing your Astro configuration or your project's dependencies invalidates the entire cache, since those can affect the output of every page." RFC lists the global signals as a cache-format version plus a hash of an output-affecting config subset (`site`, `base`, `trailingSlash`, `build.format`, `compressHTML`, `scopedStyleStrategy`), and notes as an unresolved question that "The set of config fields treated as output-affecting is maintained by hand."

**RFC status.** `withastro/roadmap#1404` "Incremental static builds", **Stage 3, still open** as of 2026-08-22 (GitHub API: `state: open`, `merged: false`, created 2026-07-25, updated 2026-08-22). Implementation PR `withastro/astro#17084` by matthewp, merged into 7.2.0. Adoption strategy per RFC: "Ships behind an experimental flag while the Stage 3 RFC iterates, then graduates to on by default in a later minor."

Note one stale detail: the *PR description* on #17084 says `dist/` must persist between builds. The shipped behaviour and the docs say otherwise (§4). The docs are authoritative here; the PR body was written against an earlier design.

### Maturity signals

Eleven `incrementalBuild` issues were filed between 2026-08-06 and 2026-08-19 — one every ~1.2 days since release. Representative:

- [#17615](https://github.com/withastro/astro/issues/17615) cache miss on image imports (7 Aug)
- [#17642](https://github.com/withastro/astro/issues/17642) / [#17652](https://github.com/withastro/astro/issues/17652) Fonts API defeated caching entirely — fixed in 7.2.2 by PR #17659: "Fixes the Fonts API breaking `experimental.incrementalBuild` caching by embedding a build-local, randomly-assigned server port in generated code used for the dependency hash"
- [#17616](https://github.com/withastro/astro/pull/17616) (in 7.2.1) — nondeterministic dependency hash: "The route's dependency hash depended on the order the assets finished building, so two builds of identical sources could produce different hashes."
- [#17630](https://github.com/withastro/astro/pull/17630) (in 7.2.2) — "Fixes incremental builds becoming prohibitively slow for sites with many pages or content entries that share a large dependency graph."

The most serious is a **silent stale-output correctness bug**: [#17704](https://github.com/withastro/astro/issues/17704), opened 2026-08-15 against 7.2.1, static output, no adapter:

> "IncrementalBuild: cached pages emit HTML referencing `_astro/*.css` files missing from build output (silent 404s)"
> "Cause: cache validity is decided from input source hashes … CSS-only edits change output asset hashes without changing the hashed inputs for content routes, so stale HTML is reused."
> "Actual: build green, production pages load a 404 stylesheet."

Fix PR [#17705](https://github.com/withastro/astro/pull/17705) merged **2026-08-19T20:47:19Z** — *after* 7.2.4 was published at 14:43Z the same day. **As of today (2026-08-23) that fix is merged but unreleased.** The root cause is instructive: "CSS modules in the prerender build have empty `code` … Because `hashModules()` was skipping modules with no code, CSS edits never changed the dependency hash". This is exactly the class of failure the RFC warned about under Drawbacks.

## 2. History of `experimental.contentCollectionCache`

The framing in the brief is **broadly right but wrong on one important detail: it never cached rendered pages.**

**Introduced: Astro 3.5.0, 2023-11-09** (not 4.x). GitHub release `astro@3.5.0`, published 2023-11-09T17:51:28Z, PR [#8854](https://github.com/withastro/astro/pull/8854) by natemoo-re:

> "Provides a new, experimental build cache for Content Collections as part of the [Incremental Build RFC](https://github.com/withastro/roadmap/pull/763). This includes multiple refactors to Astro's build process to optimize how Content Collections are handled…
>
> When this experimental feature is enabled, the files generated from your content collections will be stored in the `cacheDir` (by default, `node_modules/.astro`) and reused between builds. Most CI environments automatically restore files in `node_modules/` by default.
>
> In our internal testing on the real world Astro Docs project, this feature reduces the bundling step of `astro build` from **133.20s** to **10.46s**, about 92% faster. The end-to-end `astro build` process used to take **4min 58s** and now takes just over `1min` for a total reduction of 80%."

**What it actually cached: bundled content-collection modules — a bundling-phase artifact cache.** The quoted win is explicitly on "the bundling step". It was neither data caching nor render caching nor page-output caching. Different thing from 7.2's `incrementalBuild` in every respect.

(Spelling note: the 3.5.0 release notes use `contentCollectionCache`; the 5.0 removal entry and the v5 upgrade guide use `contentCollectionsCache`. Both spellings appear in official sources.)

**Removed: Astro 5.0.0, 2024-12-03** (npm publish time 2024-12-03T10:57:54Z). PR [#12081](https://github.com/withastro/astro/pull/12081), in `packages/astro/CHANGELOG.md`:

> "Removes the experimental `contentCollectionsCache` introduced in `3.5.0`.
>
> Astro Content Layer API independently solves some of the caching and performance issues with legacy content collections that this strategy attempted to address. This feature has been replaced with continued work on improvements to the content layer."

The v5 upgrade guide lists it under removed experimental flags whose "corresponding features are not part of Astro v5.0": <https://docs.astro.build/en/guides/upgrade-to/v5/>

The parent RFC `withastro/roadmap#763` ("Incremental Build RFC", opened 2023-11-08) was **closed unmerged on 2024-11-26**, with a maintainer noting the experimental feature was removed in Astro 5 and that "With the introduction of Content Layer the internals of how Content Collections have changed quite a lot, so how an incremental build could work needs to be rethought."

So: incremental builds were attempted in 3.5, abandoned in 5.0, left dormant for ~20 months, and re-approached from a completely different angle (page-output caching rather than module caching) in RFC 0062 → 7.2.0.

## 3. What the Astro 5+ Content Layer caches — data only

**This is incremental *data loading*, not incremental rendering.** Confirmed directly.

Astro 5.0 blog (2024-12-03, <https://astro.build/blog/astro-5/>) describes the content layer as a unified API where "Astro loads the data from all of these sources and caches the collections in a single, type-safe data store", claiming up to 5x faster Markdown builds and 25–50% lower memory. Those are *loading* and *store* wins.

Content loader reference (<https://docs.astro.build/en/reference/content-loader-reference/>):

> `LoaderContext.meta` — "A key-value store scoped to the collection, designed for things like sync tokens and last-modified times. This metadata is persisted between builds alongside the collection data but is only available inside the loader."

> `DataEntry.digest` — "An optional content digest for the entry. This can be used to check if the data has changed." When setting entries, "the entry will only update if the digest does not match an existing entry with the same ID."

Nothing in the content layer skips rendering. Prior to 7.2.0, a loader could skip re-fetching and re-parsing every entry and Astro would still render all 50,000 pages. The clearest confirmation is the RFC 0062 motivation itself:

> "Astro 7 made large-site builds substantially faster by speeding up the **bundling** phase: Rolldown replaced Rollup, and Markdown/MDX processing moved to a native Rust pipeline. What remains is the **generation** phase, where Astro renders each prerendered route to HTML. Today Astro regenerates every static page on every build, even when its template, dependencies, and data are identical to the previous build."

Astro 7.2.0 also added `digest` to public `CollectionEntry` types specifically so it can be used as a `cacheKey` — the two layers were only wired together in 7.2.0, and only via user code that the author must write by hand:

> "Adds the optional `digest` property to content collection entries. Loaders can provide an opaque digest value that changes when an entry changes."
> — `packages/astro/CHANGELOG.md`, 7.2.0, PR #17084

**Bottom line: the four caches are distinct and Astro now has three of them.** Data caching (content layer, since 5.0, stable). Bundle-artifact caching (3.5–4.x only, removed). Render/output caching (7.2.0, experimental). True whole-pipeline incremental build — not present; sync and bundle still run in full every time.

## 4. Partial output diff for deploy — no

**Every build produces a full `dist/`.** Docs, "Preserving the cache between builds":

> "Astro stores the incremental cache in your project's `cacheDir`, which is `node_modules/.astro/` by default. This holds both the build manifest and the reusable output of previously-rendered pages. **The output directory is emptied at the start of every build, and skipped pages are restored from `cacheDir`.**"

CHANGELOG 7.2.0 says the same: "Astro empties the output directory on each build and restores skipped pages from the cache directory, so only that directory needs to persist."

Consequences:

1. There is no "changed files only" output mode. A deploy step sees a freshly written full tree with fresh mtimes on every file, cached or not.
2. **No API surfaces which pages were skipped.** `astro:build:done` provides `{ pages: { pathname: string }[], dir, assets, logger }` and `astro:build:generated` provides `{ dir, logger }` — neither carries cache metadata (<https://docs.astro.build/en/reference/integrations-reference/>). The `cacheManifest` argument that the old 3.5-era cache passed to `astro:build:done` was removed in 5.0 along with the feature (PR #12081: "The `cacheManifest` boolean argument is no longer passed to the `astro:build:done` integration hook"). Nothing replaced it in 7.2.0.
3. The `incremental-build.json` manifest in `cacheDir` does record, per path, the `cacheKey` and relative output file path. It is an internal, undocumented, versioned-format file — the RFC explicitly reserves the right to bump a "Cache version … when the cache format changes." Building a deploy tool on it would be reading a private structure.

**On hash stability:** an external content-hash diff-and-upload tool (rsync/S3 style) would work in principle, because skipped pages are restored byte-identical from cache. For hashed asset filenames, Astro 7 uses Rolldown via Vite; those names are content-derived, so they should be stable when inputs are unchanged — but **I found no primary source stating a cross-build determinism guarantee for Astro output filenames**, and there is direct evidence that Astro's own hashing has had nondeterminism bugs this month (PR #17616: "two builds of identical sources could produce different hashes"). Treat determinism as plausible-but-unwarranted, not documented.

So: an external diff tool can be layered on top, but Astro contributes nothing to it. Manifest-diff partial redeploy is not a feature Astro has, has proposed, or has an RFC for.

## 5. Real-world build times and scaling limits

### Published numbers (the only official large-site benchmarks I found)

Astro 7.0 blog, 2026-06-22 (<https://astro.build/blog/astro-7/>) — full (non-incremental) build times before → after Astro 7:

| Site | Pages | Astro 6 | Astro 7 |
|---|---|---|---|
| docs.astro.build | ~6,313 | 114.54s | 73.53s |
| developers.cloudflare.com | 8,431 | 386.89s | 261.94s |
| aspire.dev | 13,275 | 385.84s | 326.11s |

Astro 7 headline: builds "15–61% faster", Rolldown replacing Rollup ("10-30x faster than Rollup in benchmarks"), a Rust `.astro` compiler, and the Sätteri Rust Markdown/MDX pipeline which "shaved over a minute off their build times" for the Astro and Cloudflare docs.

Extrapolating the aspire.dev figure (13,275 pages / 326s ≈ 24.6ms per page, and it is the *worst* per-page scaler of the three) puts a 50,000-page full build at roughly **20 minutes** — against our §16 target of 10 minutes. Treat that as an order-of-magnitude estimate, not a measurement.

I found **no official Astro benchmark at 50k pages, and no published scaling guidance or documented page-count limit.**

### Documented failure modes at scale

All verified directly via the GitHub API. Note that most are closed, several as "not planned":

| Issue | Scale | Symptom | Version | State |
|---|---|---|---|---|
| [#17604](https://github.com/withastro/astro/issues/17604) | ~225,000 md entries (5k posts × 45 locales) | OOM during Rolldown bundling; "Heap climbs to ~4 GB, GC cannot reclaim (mu degrades 0.246 → 0.015)" | 7.1.6, static, **no adapter** | closed 2026-08-12 |
| [#14893](https://github.com/withastro/astro/issues/14893) | 10,000 md files, <30 MB total | "With 6GB RAM limit: 10+ minutes … With 16GB RAM limit: Completes in seconds"; "I would not expect 10.000 simple text markdown files with a total size of <30mb to consume over 6GB of RAM during build." | 5.16.0, static, no adapter | closed 2025-12-09 |
| [#16297](https://github.com/withastro/astro/issues/16297) | 1,000 entries, 1,000 pages | `getCollection()` re-walks every entry for image refs on each call; "48 seconds of additional build time on production site" | 6.1.5 | closed 2026-06-05 |
| [#17301](https://github.com/withastro/astro/issues/17301) | Starlight docs w/ KaTeX | OOM during content sync; loader "eagerly renders Markdown/MDX entries and stores the rendered output in the global content data store" | 7.0.6 | closed 2026-07-15 |
| [#12888](https://github.com/withastro/astro/issues/12888) | 100,000+ md files | heap OOM even at `--max-old-space-size=12288` | 4.x | closed **not planned** 2025-01 |
| [#11683](https://github.com/withastro/astro/issues/11683) | 30,000 MDX files | OOM at 8 GB; then "the build fails abruptly with a 'Killed' message" | 4.13.3 | closed **not planned** 2024-08 |
| [#10485](https://github.com/withastro/astro/issues/10485) | 500,000+ md files | heap OOM | 2024-04 | closed |
| [#7241](https://github.com/withastro/astro/issues/7241) | 4,000+ content files | `EMFILE: too many open files` | — | closed |

Memory pressure remains active in the current line: `astro@7.2.3` (2026-08-18) shipped PR #17724 — "Fixes an issue where Astro could run out of memory when `experimental.collectionStorage` is set to `chunked` and there are multiple concurrent updates to the same collection" — and `astro@7.2.2` shipped PR #17650 fixing `EMFILE` exhaustion "on projects with many images."

The pattern across every one of these: memory is retained proportionally to total content volume, not to changed content. **`incrementalBuild` does not address this at all** — sync and bundle still process the entire corpus. A 50k-page site that OOMs on a full build will OOM identically on an incremental one.

### Concurrency is capped at 1

`build.concurrency`, added in `astro@4.16.0`, default `1`. Docs (<https://docs.astro.build/en/reference/configuration-reference/>) advise "in most cases, you should not change the default value of `1`", and warn that raising it can slow rendering "due to insufficient memory resources and because JS is single-threaded." `incrementalBuild` requires it to be `1` anyway. Astro's page generation is effectively single-threaded.

### Incremental-build cost at scale, measured

[#17702](https://github.com/withastro/astro/issues/17702), filed 2026-08-14 against 7.2.2 (static output, Cloudflare adapter), closed as completed 2026-08-15:

> "During the build process, restoring the dependency cache and build output cache is taking an unusually long time (over 35 seconds total for 10k pages)."
> `03:52:21.159 — Dependencies restored from build cache (18.93s elapsed)`
> `03:52:37.435 — Build output restored from build cache (16.27s elapsed)`

16 seconds just to restore cached output for 10k pages in CI, before any Astro work begins. Against our 30s end-to-end incremental target at 50k pages, this is the single most relevant real-world datapoint I found — and it is cache *restoration alone*, excluding content sync, bundling, and the render of changed pages.

I did **not** find a maintainer-published incremental-build benchmark. The 7.2 release post does not contain benchmark numbers for the feature. (Third-party numbers circulate — e.g. a claim of 637/661 pages restored and ~16.5s → ~10s — but those are secondary sources and are **not** treated as evidence here.)

RFC 0062 remains **open at Stage 3**, actively contested. From the PR discussion, unresolved design objections raised by core members include: the restriction to `getStaticPaths()` routes excluding single routes and endpoints; the requirement to centralise all data inputs at the route top level, which cuts against component-level data isolation and hurts dev-time performance on large sites; no provided utility for hashing composite cache inputs (passing an object yields the string `"[object Object]"`); and the `build.concurrency = 1` restriction, which stems from "concurrent renders overwrite each other's collection" in global tracking state and is acknowledged as temporary. An alternative component-level `getStaticData()` API was proposed and pushed back on. **The public API of this feature should be expected to change before it stabilises.**

## 7. Implications for our §16 targets

Stated plainly, because the brief asked for the true answer:

**"Astro has no incremental builds" is dead as a positioning claim.** As of 2026-08-06 it does, it caches rendered output, and it will graduate to on-by-default in a later minor per the RFC's adoption strategy. Any pitch deck line to the contrary is falsifiable by anyone who reads the 7.2 release notes.

What is still ours, and each of these is defensible against a primary source:

1. **Automatic change detection.** Astro's is an explicit non-goal — "Astro does not infer when a CMS entry or other external data has changed" — with a documented failure mode of silently stale pages. A framework that owns its own content store can derive keys itself. This is the largest remaining gap and it is architectural, not a matter of time.
2. **Coverage of all routes.** Astro covers dynamic routes with a `cacheKey` only. Single routes, endpoints, and any page not using `getStaticPaths()` re-render every build, by design.
3. **Incremental across the whole pipeline.** Astro's dependency hash is computed *from* the bundle, so bundling and content sync are unconditionally full. Our 30s-at-50k-pages target is not reachable by Astro's design, because its incremental path still pays full sync + full bundle. Issue #17702 (16s just to restore 10k cached pages in CI) suggests it is not close today even on the parts it does optimise.
4. **Manifest-diff partial redeploy.** Astro empties `dist/` every build and exposes no skipped-page information through any hook. There is no RFC for this. Ours is uncontested.
5. **The 50k scale envelope.** Documented OOM at 10k files under 6 GB, at 30k MDX, and at 225k entries — the last one on 7.1.6, static, no adapter, in the Rolldown bundler itself. `incrementalBuild` does not help here, since the failures are in phases it does not skip. Astro publishes no scaling guidance and closed several of these "not planned."
6. **Parallelism.** Astro generation is effectively single-threaded (`build.concurrency` default 1, advised against changing, and forced to 1 by `incrementalBuild`).

The honest summary for the maintainer: *the maintainer is right that Astro has this now, and the differentiator has narrowed from "we have incremental builds and they don't" to "ours is automatic, whole-pipeline, covers every route, and emits a deploy diff — theirs is opt-in, render-only, dynamic-routes-only, and hands you a full `dist/` regardless."* That is a real difference, but it is a difference of degree that has to be demonstrated with numbers at 50k pages, not asserted.

## What remains unverified

Listed honestly; each of these would change the confidence of a claim above.

1. **No first-party incremental-build benchmark exists.** The 7.2 release post ships no numbers for the feature. I have no maintainer-published measurement of incremental rebuild time at any page count. Every figure quoted in §5 is either a full-build number or a user bug report.
2. **Behaviour at 50k pages with `incrementalBuild` enabled is untested by anyone I could find.** The only large-scale datapoint is #17702 at 10k pages, and it measures CI cache restoration, not Astro's own work. Whether the sync + bundle floor at 50k is 60s or 600s is unknown. **If we want a defensible comparison, we should build a 50k-page Astro 7.2 fixture and measure it ourselves.** That is the single highest-value follow-up.
3. **Output filename determinism across builds is undocumented.** I could not find any Astro or Rolldown statement guaranteeing stable content-hash filenames across rebuilds with unchanged inputs. Astro's own hashing had a nondeterminism bug fixed this month (#17616). Whether an external diff-and-upload tool is reliable on Astro output is therefore *unresolved*, not merely unproven.
4. **The `incremental-build.json` schema is undocumented.** The RFC names the file and its contents at a high level; I did not read the implementation to confirm the exact shape, and the RFC reserves the right to change it under a cache-version bump.
5. **Whether `incrementalBuild` will graduate, and in what shape.** RFC 0062 is open and its central API (`cacheKey` on `getStaticPaths()`) is under active challenge from a core member proposing a component-level `getStaticData()` alternative. The stable form may look materially different from what 7.2 ships.
6. **The `build.concurrency = 1` restriction is called temporary** in the RFC discussion, to be lifted via request-scoped tracking. No PR or timeline for that was found. If lifted, Astro's per-page cost could drop substantially.
7. **RFC 0062 discussion content** was read via a page summariser rather than raw API for the comment thread specifically; the quoted objections in §6 are attributed to named members in that summary but I did not verify each attribution against the raw comment JSON. The RFC document itself (§1, §3) was fetched raw and is fully reliable.
8. **Astro 5's Content Layer performance claims** (5x Markdown, 25–50% memory) are the vendor's own, unaudited, and measured on their own docs site.
9. **The `contentCollectionCache` removal rationale** is only ever stated as "the Content Layer solves this better." I found no bug-driven justification, and no maintainer post-mortem explaining whether the 3.5 cache was also producing stale output. If it was, that history is relevant to how much to trust the 7.2 cache.
